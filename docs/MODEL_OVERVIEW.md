# Модель торговли: быстрый контекст

Документ для того, чтобы за 5 минут понять, как устроена «модель» бота, где что лежит и как проверять. Полный список функций: [MODEL_FUNCTIONS.md](MODEL_FUNCTIONS.md) (генерируется `python scripts/list_functions.py > docs/MODEL_FUNCTIONS.md`). Результаты аудита: [MODEL_AUDIT.md](MODEL_AUDIT.md).

## Из чего состоит

| Слой | Файлы | Что делает |
|---|---|---|
| Сигнал стратегии | `app/services/strategy_engine.py` | По свечам 1 мин даёт BUY/SELL/HOLD и score. Режимы: `trend`, `mean_reversion`, `breakout` (`evaluate_signal`). Это единственный «классический» источник сигналов. |
| Признаки | `app/ml/feature_builder.py`, `multi_timeframe.py` | `build_features` собирает 30 признаков (`FEATURE_NAMES`): z-score, SMA-gap, momentum, пробой, объём, ATR, тренд/волатильность 1ч и 4ч, стакан, RSI/MACD/BB, время суток, VWAP, фаза сессии, режим рынка, корреляция с SBER/GAZP, код тикера, риск переноса шорта. |
| ML-модель | `app/ml/model_trainer.py`, `model_predictor.py` | `GradientBoostingClassifier` + калибровка Platt, предсказывает P(сделка прибыльная). Модели хранятся в таблице `ml_models` (pickle), одна активная на бумагу + одна универсальная на все бумаги. |
| Решения по модели | `model_predictor.py` | Фильтр входа `should_enter` (порог 0.60, жёсткое вето только после 100 сделок, ниже — мета-правило «2 из 3»: score, тренд 1ч, P), досрочный выход `should_exit_early` (P < 0.30, держать не менее 20 мин), масштаб лота `compute_lot_scale`, адаптивные SL/TP `compute_adaptive_sl_tp`, ранжирование бумаг `rank_instruments`. |
| Обучение на опыте | `app/ml/experience.py`, `analyzer.py`, `optimizer.py`, `strategy_selector.py`, `orchestrator.py` | Контекст каждой сделки (`ml_trade_context`), качество стратегии (expectancy, EWA), подбор SL/TP/min_score координатным спуском, выбор режима стратегии Thompson Sampling, суточная перебалансировка и детектор дрейфа. |
| Бэктест и аналитик | `app/services/backtest_engine.py`, `analyst.py`, `app/ml/backtest_client.py` | Прогон стратегий на истории, поиск лучших параметров, сохранение результата как стратегии. |

## Жизненный цикл решения (main.py)

1. Воркер стратегии берёт свечи, `_evaluate_signal(tradingmode, candles)` → сигнал и score.
2. Фильтры без ML: сессия, лимиты (сделок/убытка за день), cooldown, баланс, встречная позиция по бумаге (защита от неттинга, v5.8.9).
3. `build_features` → `should_enter` (ML-вето/мета-правило). Если вход разрешён: `compute_adaptive_sl_tp`, `compute_lot_scale`.
4. Ордер → нативные SL/TP на бирже → `record_entry` (контекст) и `store_features` (признаки без метки).
5. Пока позиция открыта: программные SL/TP в цикле, `should_exit_early` по ML.
6. Закрытие (бот, биржевой стоп или вручную): `add_trade` → `label_features` (метка по PnL) → `on_trade_closed` (быстрое EWA-обновление) → `record_exit` → при накоплении 10 новых сделок `train_model`.
7. Раз в сутки (00:00 МСК) `run_daily_rebalance`: обучение универсальной модели, глубокий анализ по бумагам, ранжирование, детектор дрейфа. Он **меняет режим и SL/TP боевых стратегий**, запускать вручную осторожно.

## Таблицы БД

`ml_features` (признаки и метка), `ml_virtual_trades` / `ml_virtual_paths` (виртуальные сделки и поминутный путь цены), `ml_models` (pickle-модели и метрики), `ml_decisions` (журнал решений), `ml_trade_context` (контекст сделок), `ml_instrument_state` (EWA-качество и выученные параметры по бумаге), `ml_optimization_log` (история оптимизаций). Связь с торговлей: `trades`, `positions`, `strategy_instruments`, `strategy_settings`.

## Виртуальные сделки (v5.10.0)

Реальных сделок мало (лимиты позиций, паузы, фильтры), поэтому модель получала метки на десятках примеров, а решения самой модели ещё и сужали выборку. Виртуальный контур отрабатывает **каждый новый сигнал без брокера** и записывает исход.

- **Поток** `virtual-scanner` (`main.py: _virtual_scanner_worker`, логика в `app/ml/virtual_scanner.py`): раз в ~5 с обходит инструменты основного цикла и всех активных параллельных стратегий; когда у бумаги появляется новая завершённая свеча, считает все три режима (trend, mean_reversion, breakout) по тем же свечам, что и воркеры. Фильтры реальной торговли (`min_signal_score`, лимиты, пауза, решения модели) на создание сделки не влияют; результат фильтров пишется в `ml_virtual_trades.filter_stage`.
- **Эпизод** — серия подряд идущих сигналов одного режима и направления по бумаге; новый эпизод начинается после паузы 150 с без сигнала. На эпизод — одна сделка, иначе выборка превратилась бы в повторы одного и того же.
- **Движок** (`app/ml/virtual_trades.py`): вход BUY по ask / SELL по bid, SL/TP от цены входа (из настроенной стратегии для этого режима, иначе 0.8% / 1.5%), комиссия 0.04% с каждой стороны, выход «по рынку» учитывает спред. Закрытие: SL/TP по тикам из стрима, таймаут 120 минут или конец сессии (18:45 / 23:45 МСК); через перерыв и ночь сделки не живут. Метка: чистый результат > 0 → 1, иначе 0.
- **Хранится** в `ml_virtual_trades` (итог, MFE/MAE, результат через 5/15/30/60 минут, фильтры, вероятность модели, `ind_missing`), `ml_virtual_paths` (поминутный путь цены, чистится через 30 дней) и в `ml_features` (`source='VIRTUAL'`, `strategy_mode`, `virtual_id`; метка и причина выхода проставляются при закрытии). Из `trades`, `positions`, дневного PnL, EWA и дашбордных реальных счётчиков виртуальные сделки исключены.
- **API:** RSI/MACD/BB берутся из API (общий кеш 90 с с боевым путём), свечи — из общего кеша воркеров. Собственные запросы контура ограничены скользящим бюджетом (половина лимита API, сейчас 285 в минуту) и уступают реальной торговле: при общей нагрузке ≥ 480 запросов в минуту контур запросов не делает. Нет бюджета — индикаторы остаются пустыми, сделка помечается `ind_missing=1`, значения не выдумываются.
- **Настройка** `virtual_trades_enabled` (по умолчанию `1`; `0` — не открывать новые сделки, открытые дорабатывают). После остановки бота незавершённые сделки помечаются `ABORTED` и метки не получают.
- Пока модель не переучена новым тренером (Этап 4), старый тренер виртуальные строки **не использует**.

### Историческая добивка (v5.11.0)

`scripts/backfill_virtual.py` проигрывает минутные свечи за прошлые дни теми же правилами, что и живой контур, и записывает результат с `source='BACKFILL'`. История минутных свечей доступна минимум на 2 года (проверено пробой `scripts/backfill_probe.py`).

- **Запуск** (на сервере, из каталога проекта): `nice -n 19 .venv/bin/python scripts/backfill_virtual.py --days 60` — пробный прогон, БД не меняется; с `--apply` — бэкап в `backups/` и запись. Повторный запуск безопасен (эпизод пропускается по `episode_id`). Свечи прошлых дней кешируются в `data/backfill_cache`. Запросы идут с потолком `--rpm` (по умолчанию 100 из 600 в минуту).
- **Признаки на момент сигнала без заглядывания в будущее** (`app/ml/virtual_backfill.py`, проверено тестом: признаки не меняются, если отрезать свечи после сигнала): окно свечей 55 минут, как в боевом пути; RSI/MACD/BB считаются локально по свечам за последние 3 часа, формулы совпадают со значениями `GetTechAnalysis` до 5-го знака; 1ч/4ч свечи собираются из минутных окнами 96/160 часов; время суток, фаза сессии, риск переноса шорта (`build_features(as_of=…)`) и корреляция с SBER/GAZP — на момент сигнала.
- **Чего в истории нет:** стакана (`bid_pressure`, `book_depth_ratio`, `spread_pct` пишутся как NULL, не нейтральные значения) и спреда (вход/выход считаются с фиксированным 0.05%, `fill_src='synthetic'`). Порядок движения цены внутри свечи неизвестен, берётся худший для сделки: стоп раньше тейка.
- **Границы:** добивка заканчивается там, где начинается живой контур. В дашборде добивка считается отдельной строкой и в срезах живых сделок не участвует. Старый тренер её не использует.
- Календарь праздников вынесен в `app/services/moex_calendar.py` (признаки больше не импортируют `main.py`).

### Сделки без ограничения по времени (v5.13.0)

Цель владельца — торговать в плюс по итогам дня, а сделка не должна ограничиваться временем. Для этого `VirtualEngine(hold_until_exit=True, light=True)` держит виртуальную сделку до SL или TP, в том числе через ночь и выходные; исход чистый — «тейк раньше стопа» (без смещения от срока жизни); новые сигналы по-прежнему открываются только в торговую сессию. Облегчённый режим (`light`) проверяет SL/TP по минутной свече без пути цены и контрольных точек (сотни долгих сделок открыты одновременно). Внутри свечи при задетых стопе и тейке засчитывается стоп; стоп внутри свечи исполняется по уровню, гэп через стоп — по цене открытия (раньше в режиме свечей стоп исполнялся по минимуму свечи, что завышало убыток истории).

Что показала история (60 дней, 118 764 эпизода, `scripts/backfill_virtual.py --fetch-only` + локальный анализ): медианное время до SL/TP 14.5 ч, у 25.6% сделок больше суток; доля тейков 34.3% при безубыточной ≈ 38–43%. **Перекос BUY/SELL следует за направлением рынка по неделям** (в растущие недели покупки берут тейк в 44–53%, продажи в 18–24%; в падающие наоборот), то есть результат — ставка на направление рынка, а не навык сигналов; модель выучила этот перекос и ломается при развороте. Итог по дням (до 12 позиций, 1/12 капитала на позицию): без отбора −0.89% в день, только покупки −0.11% при 45% плюсовых дней, худший день −2.4%. Каждый день в плюсе эти сигналы не дают.

### Цель обучения: доходность вперёд (v5.12.0)

Метка «чистый итог сделки > 0» смещена временем жизни сделки (сделки поздно в сессии закрываются принудительно и коротки, а короткие почти всегда «в минус» из-за издержек): на ней главными признаками становились час и день недели, а отобранные моделью сделки не были прибыльнее остальных. Поэтому цель — **доходность через 15/30/60 минут после сигнала** (`ml_virtual_trades.fwd_ret_15m/30m/60m`, % от цены рынка в момент сигнала, в сторону сделки, без издержек), не зависящая от SL/TP и таймаута. Движок после закрытия сделки по SL/TP продолжает дослеживать цену до нужных горизонтов (но не за пределы своей сессии); для истории значения проставляются тем же движком (`scripts/backfill_virtual.py --refresh-targets`).

- **Издержки** (`app/ml/trainer_v2.py`): комиссия брокера 0.05% за сторону (факт по операциям песочницы: 251 операция, ровно 0.0500%; оценка бота 0.04% занижена) + спред бумаги по живым наблюдениям (в среднем 0.024%: SBER 0.004% … ALRS 0.065%).
- **Тренер v2** (`scripts/train_v2.py`): регрессия `HistGradientBoostingRegressor` на доходности вперёд; признаки без `regime`, `position_minutes`, `ticker_hash`, `day_of_week`, плюс `is_evening` и флаги режима; NaN допустимы (в истории нет стакана). Валидация хронологическая с зазором в сутки, эпизоды одной бумаги в одном 30-минутном блоке имеют суммарный вес 1. Метрика — **средний чистый итог отобранных сделок** (верхние 50/20/10/5/2/1% по прогнозу) с 90%-интервалом блочного бутстрапа и числом фолдов с положительным итогом. Вердикт «подтверждено на истории» выдаётся, только если нижняя граница интервала > 0, выборка ≥ 300 и итог положителен почти во всех фолдах; иначе — «преимущество не доказано».
- Результат (`--apply`) — кандидат в `ml_models` (`figi='UNIVERSAL_V2'`, `status='candidate'`) и отчёт в `ml_training_reports`. **В торговлю кандидат не попадает**; включение (`ml_enforce`) — только после теневого периода на новых живых данных.

## Ключевые пороги

| Константа | Значение | Смысл |
|---|---|---|
| `ENTRY_THRESHOLD` | 0.60 | P выше — вход |
| `HARD_VETO_MIN_SAMPLES` | 100 | с этого числа сделок порог становится жёстким |
| `EXIT_THRESHOLD` / `MIN_HOLD_MINUTES` | 0.30 / 20 | досрочный выход |
| `MIN_SAMPLES` / `RETRAIN_EVERY` / `TEST_RATIO` | 30 / 10 / 0.2 | обучение: минимум, частота, доля теста (последние по времени) |
| `MIN_PRECISION_ACTIVATE` | 0.50 | минимальная precision для активации универсальной модели |
| `MIN_STOP_LOSS_PCT` (main.py) | 0.5% | пол стопа |
| `EWA_ALPHA` / `MIN_TRADES` | 0.2 / 5 | сглаживание качества |
| `ml_enforce` (bot_settings, по умолчанию `0`) | 0 / 1 | 0 — «тень»: решения модели (`entry_shadow_block`, `early_exit_soft`) пишутся в `ml_decisions`, но вход не блокируется и позиции не закрываются; 1 — модель применяет вето и досрочный выход (v5.9.3) |
| `md_stream_workers` (bot_settings, по умолчанию `1`) | 0 / 1 | 1 — стрим цен и стакана слушает и инструменты параллельных воркеров (v5.9.6); 0 — как раньше, только инструменты основного цикла, воркеры берут цену и стакан по REST. Включение даёт воркерам настоящие признаки стакана и **включает фактическую работу фильтра давления стакана** (`use_order_book_filter`), раньше не срабатывавшего из-за нулевых объёмов REST-стакана |
| `POLICY_EXIT_REASONS` | `STOP_LOSS`, `TAKE_PROFIT` | в обучение идут только строки с такой причиной выхода (`ml_features.exit_reason`) или с неизвестной (NULL); ранний выход модели, ручное закрытие и ремонт учёта метку не несут |

## Как проверить модель

- Данные и логи сервера: MCP `trading-bot-server` (локально, в git не хранится): `trade_stats`, `run_select`, `get_events`, `error_summary`.
- Тест на копии БД (не на продакшне): снимок `sqlite3 data/trading_bot.sqlite3 ".backup /tmp/x.sqlite3"`, запуск с `DB_PATH=/tmp/x.sqlite3`.
- Что нельзя запускать на продакшне ради проверки: `run_daily_rebalance`, `_apply_*` в `orchestrator.py` (меняют боевые настройки).

## Известные ограничения

- Реальных размеченных сделок мало (около сотни), поэтому с v5.9.3 модель работает в «тени» (`ml_enforce=0`): включение любой активной модели раньше запускало мета-правило «2 из 3» (в основном `score<20` у режима trend), заблокированные сигналы не получали меток, и выборка переставала расти. Включать `ml_enforce=1` только после проверки модели на данных, не зависящих от её решений (виртуальные сделки, v5.10).
- Брокер ведёт позицию нетто по бумаге, модель и учёт — по стратегиям; расхождения ловит `POSITION_MISMATCH`.
- Sandbox-цены и ликвидность не равны реальным, метрики модели нельзя переносить на боевой счёт без повторной проверки.
